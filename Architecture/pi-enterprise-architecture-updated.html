Co-Pilot for PI: enterprise architecture

A governed, read-first agentic layer that sits beside Jira, GitHub and Confluence at Haverstone Financial Group, finds the dependencies nobody wrote down, shows its reasoning, and hands every consequential decision back to a named human.

Prepared for the Dallas Got AI Talent challenge · Haverstone case study · Inputs reviewed: case brief, PI planning wireframes (4 screens), Nexlara sample brief (used as a format reference for the architecture deliverable)

1. Summary

Haverstone plans 38 teams across 6 Agile Release Trains every 10 weeks. About a third of dependencies surface only at the planning event, and roughly 19% only mid-PI. The most damaging ones live in code (shared libraries, internal APIs) or in aggregate demand on Core Banking & Ledger, which no tool sums today.

The architecture has five ideas:

  1. Evidence graph, not a score. Every dependency is an edge in a typed graph with provenance (which Jira epic, GitHub manifest, Confluence page or ServiceNow record produced it) and a confidence level. Nothing appears in the UI without a traceable source.
  2. Deterministic where regulated, probabilistic where ambiguous. LLMs read prose and propose candidate edges. Rules and graph algorithms (cycle detection, capacity sums, ownership checks) decide the Dependency Risk Index patterns. The model never computes a capacity number or declares a cycle.
  3. Read-only by default, propose-only for writes. The system reads Jira, GitHub, Confluence, ServiceNow and Archer. It can only draft Jira changes into an approval queue. It never touches code, never assigns an owner, never commits a plan.
  4. Inferred capture. EMs and POs do no new tagging. GitHub manifests and the service ownership map generate most candidate edges; humans confirm or reject.
  5. Living record. After the event, a change monitor re-evaluates agreed dependencies when upstream epics, dates or manifests move, and routes the change to the owning EM before it becomes a mid-PI surprise.
Scope statementPhase 1 (90 days) delivers extraction, graph, DRI engine, Core Banking & Ledger capacity radar, transparent sequencing and the reasoning drawer, all read-only with an approval queue for Jira link proposals. Living-record monitoring and ART-wide rollout follow in Phases 2 and 3.

Every constraint in the case brief maps to a concrete architectural decision.

Principles

  • Separate reasoning from authority. Agents reason; people and systems of record decide.
  • Remember what is reusable, recompute what is initiative-specific. Service ownership, consumer lists and manifest edges persist in the graph. Per-PI demand, sequencing and risk are recomputed each run from a versioned snapshot.
  • Every output is reproducible. A run pins snapshot version, prompt versions, model version and rule-set version, so a finding can be re-derived for audit.
  • Fail visible, not silent. A source that cannot be read downgrades coverage and says so on screen; it never produces an unmarked partial answer.

4. Agent design

The wireframe shows five agents (Initiative analyser, Dependency discovery, Sequencing, Risk, Visualisation). The architecture keeps those names and adds a Capacity radar, because the brief makes Core Banking & Ledger overcommitment (~145%) a first-class failure and a pure LLM cannot be trusted to sum it. Each agent has a narrow contract: typed input, typed output, and a declared split between model and code.

Agent boundaries (guardrails by construction)

  • Agents receive tools through the orchestrator's allow-list. Only the write-back service holds a Jira write credential, and agents cannot call it directly.
  • An agent's structured output is validated against a JSON schema; invalid output is retried once with the validation error, then escalated as a failed step. Free text is never passed to downstream agents unvalidated.
  • Retrieved text (Jira comments, Confluence, repo READMEs) is treated as untrusted data. It is delimited, never concatenated into system instructions, and instruction-like content is logged as a possible injection attempt.

5. Data and knowledge architecture

Core model

Node types

  • Initiative, Epic (from Jira / initiatives.csv)
  • Team, ART (team_directory)
  • Service, API, Dataset, LedgerCapability (service_ownership_map)
  • Repository, Library (github_repos)
  • Control (Archer sign-off requirement)
  • Decision (human outcome on a finding)

Edge types

  • BLOCKED_BY, REQUIRES (explicit text)
  • IMPORTS, CALLS, SHARES_LIB (code)
  • WRITES_TO, READS_FROM (implicit shared target)
  • OWNED_BY, CONSUMED_BY
  • GATED_BY (control sign-off)

Every edge carries: channel (jira-text · github · confluence · inferred), confidence, evidence_ids[], status (proposed · confirmed · rejected), first_seen, last_validated.

Stores and what each remembers

StoreHoldsLifetimeRationale
Dependency graphNodes and edges, confirmed or proposedPersistent, snapshot-versioned per PIReusable knowledge: service ownership, known consumers, manifest edges. Recomputing these each run wastes tokens and loses human confirmations.
Evidence storeExcerpts, rationale bundles, rule traces, decision recordsRetained per audit policy (see §9)Everything in the reasoning drawer resolves to a stored record.
Vector indexEmbeddings of epics, Confluence pages, dependency docsRebuilt on source changeRetrieval for the text and implicit channels only; never the source of truth.

Per-run working stateCapacity totals, sequence, risk rankingRecomputed each runInitiative-specific and PI-specific; stale the moment inputs change.

Entity resolution

The hardest data problem is not extraction but naming: "ledger posting API", "Posting Service" and "ledger-posting-svc" are one thing. A resolver maps mentions to canonical nodes using the ServiceNow-derived ownership map as the authority, then fuzzy and embedding matches with a threshold. Matches below threshold become unresolved mention items for human confirmation, and confirmations are stored as aliases so the same question is never asked twice.

6. Runtime flow

Notes on the flow

  • Step 2 (snapshot). Freezing a versioned snapshot means a re-run on the same inputs reproduces the same graph, and a diff between two snapshots drives the Phase 2 monitor.
  • Step 4 (validate). An LLM-proposed edge with no resolvable evidence reference is discarded, not shown. This is the main defence against hallucinated dependencies.
  • Steps 5 to 7 (deterministic core). Capacity totals, cycle detection and ordering are computed by code and are unit-testable against the historical PI outcomes.
  • Step 9. The UI streams partial results while later agents run (as in wireframe screen 2), but nothing becomes actionable until the run completes.

9. Security, compliance and AI governance

Haverstone is a regulated bank, so even a decision-support tool is designed as if examiners will read its logs.

Identity and access

  • SSO with RBAC scoped by ART; cross-ART views require an explicit role.
  • Separate service principals per connector; read and write principals are distinct.
  • Secrets in a managed vault with rotation; none in code or prompts.
  • Network: private endpoints, no public inbound to connectors or model gateway.

Data protection

  • Source-code content is not stored; only manifest facts, paths and ownership.
  • Classification gate on ingestion; the challenge tenant accepts synthetic data only. A production tenant would block customer or transaction data.
  • Encryption in transit and at rest; customer-managed keys in production.
  • Model provider: private endpoint, no training on inputs, zero or short retention.

Audit and traceability

  • Append-only log of every run, proposal, approval, rejection and write (actor, timestamp, rationale, versions).
  • Any finding reproducible from its run ledger entry.
  • Retention aligned to Haverstone's records policy (assumed multi-year; to confirm).

Model risk and AI governance

  • Registered in the model inventory with a risk tier. Because outputs inform but do not decide, the proposed tier is lower than for a decisioning model; model-risk confirms.
  • Offline evaluation against the last 6 PIs (historical_pi_outcomes) before each release; prompt and rule-set changes go through change control.
  • Monitoring for precision of confirmed edges, rejection rate, drift in extraction quality, and cost.

These volumes are small by data-platform standards: the architecture's difficulty is trust, entity resolution and governance, not throughput. A relational store with graph queries (or a managed graph database) is sufficient at this size; the choice is recorded as a decision in §16.

Operating model

  • Product owner: PMO lead (owns backlog, thresholds and adoption metrics).
  • Platform team: small engineering team owning connectors, graph and orchestrator.
  • AI governance: model-risk partner owns inventory, evaluation gates and prompt change control.
  • AI champions: one RTE or EM per ART who triages unresolved mentions and tunes thresholds.
  • Cost control: per-run token budget, caching of unchanged epics between snapshots (only changed items are re-extracted), cheaper model for classification and larger model only for ambiguous text.

13. Phasing

The brief favors a sharp, demonstrable slice. Phase 1 is sized so a small team can deliver it in 90 days and prove value before wider commitment.

Phase 1 · 0 to 90 days

Prove it on one ART plus Core Banking & Ledger.

  • Read-only connectors: Jira, GitHub, Confluence, ServiceNow
  • Extraction and entity resolution
  • Graph with GitHub-vs-Jira edge distinction
  • DRI-X-001, 002, 003, 004, 005 as rules
  • Capacity radar for Core Banking & Ledger
  • Transparent sequencing with reasoning drawer
  • Approval inbox for Jira link proposals
  • Audit log and offline evaluation vs last 6 PIs

Exit test: beat the 61% pre-event identification baseline on the pilot ART and surface the ledger overcommitment before the event.

Phase 2 · 90 to 180 days

Make it live and wider.

  • Living-record monitor and drift routing
  • Archer integration and regulated-item gating
  • Roll out to all 6 ARTs
  • DRI-X-006 (late-discovered) from event-time diffs
  • Notifications into Slack / Teams
  • Retire Spaghetti Sheet as source of truth

Exit test: mid-PI discovered dependencies trending toward the <5% target.

Phase 3 · 180 days onward

Extend and harden.

  • DRI-X-007 informal-channel detection (opt-in)
  • Jira embedded panel
  • Scenario modeling ("what if we defer X?")
  • Additional sources (e.g. Azure DevOps)
  • Multi-region, key management, full DR

Exit test: prep effort per ART trending from ~64 toward 24 hours.

14. Why AI-native rather than AI-assisted

  • The input is unstructured and cross-system. Dependencies exist in prose and in code. Without a model that reads both and reconciles them, there is nothing to analyse; this is the core of the problem rather than a convenience layer on a finished process.
  • Inference replaces tagging. The human role shifts from authoring dependency records to confirming or rejecting candidates, which is what keeps EM effort down.
  • The system stays alive. A tool that only helps during planning leaves the post-PI drift problem untouched. Continuous re-evaluation is only feasible when extraction is automated.
  • Learning loop. Confirmations and rejections accumulate as labeled data, improving thresholds and extraction prompts per ART, within governed change control.

The deliberate counterweight: the model is kept out of authority. This is the AI-native pattern appropriate to a regulated bank: AI does the discovery work at a scale people cannot, and deterministic code and named humans own every consequential decision.

16. Key decisions, assumptions and open items

Architecture decisions

#DecisionReasonTrade-off
1Deterministic rules and algorithms own DRI, capacity and sequencing; LLM owns language tasksAuditability and trust; testable against historical PIsLess flexible for novel patterns; mitigated by human-reviewed candidate patterns
2Propose-only write-back with approval inboxMeets the constraint on systems of record and regulated workAdds a human step; accepted deliberately

4Relational store with graph queries and vector extensionSmall data volumes; one store to governRevisit if graph traversal needs grow

Assumptions to validate

  • The data package provides enough signal in github_repos.csv (declared internal dependencies) to derive code-level edges without parsing source.
  • Jira comment and description fields can be read for all 6 ARTs under one service principal.
  • Archer exposes sign-off status by API or export; if not, Phase 1 uses a manual mapping table for regulated items.
  • Model provider terms (no training, retention) satisfy Haverstone's third-party risk review.
  • Retention and model-risk tier are placeholders pending Haverstone policy.

Open questions for coaches or stakeholders

  • Which ART is the best Phase 1 pilot: the one with the most Core Banking & Ledger dependence, or the one with the most dependable data?
  • Is "confirmed by owner" the right trust bar for automatic inclusion in the pre-PI report, or should low-confidence edges appear as a separate section?
  • Who is accountable for the ownerless-dependency decision queue between PIs?
