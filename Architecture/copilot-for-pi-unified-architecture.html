Co-Pilot for PI: one architecture, two source modes

The design is identical in the hackathon demo and in a bank deployment. The only thing that changes is the source adapter: CSV and mock files today, live Jira, GitHub, Confluence, ServiceNow and Archer later.

1. The central idea

The demo has no Jira, GitHub or ServiceNow, so every source is a file in /data. Rather than build a throwaway demo and a separate enterprise design, this architecture puts a source adapter interface between the sources and everything else. Both modes produce the same normalised records, so the context store, agents, rules, UI and audit trail never know which mode they are in.

  • Demo mode: file adapters read the provided data package plus four small mocks. Runs on one laptop.
  • Production mode: read-only connectors read the real systems. Same agents, same rules, same screens.
  • Consequence for the pitch: everything shown in the demo is real behaviour of the production design. Only the plumbing in the bottom layer is swapped, and the swap is a configuration change plus connector work, not a redesign.

4. Run flow

  1. Load. The adapters pull from the active mode, validate, resolve entities, and freeze a snapshot ID. Demo: runs once at startup. Production: scheduled pull plus change events.
  2. Intake. The user selects initiatives (or uploads a Jira-style CSV). The API starts a run and streams agent events to the pipeline screen.
  3. Analyse and discover. The analyser extracts systems; discovery runs its three evidence tools in parallel.
  4. Verify. The verifier drops ungrounded edges and re-queries weak ones, and each edge is tagged already-in-Jira or newly inferred.
  5. Sequence and score. Algorithms order the work and find cycles; DRI rules score blockers using capacity, ownership, control status and history.
  6. Review. Results and drawer show the chain and sources. The reviewer can challenge (add a constraint such as "Payments goes first", which re-runs Sequencing and Risk) or approve.
  7. Export or propose. Approved items become Jira link and sequence-note proposals plus an audit JSON. Demo: file export only. Production: the same proposals enter an approval inbox and, after named sign-off, are written by a separate least-privilege service.

7. Corrections built into this version

These come from reviewing the earlier demo plan against the case brief.

Evaluation leakageS3 (labelled dependency statements) is used both as few-shot examples and as ground truth. Split it: one portion for prompts, a held-out portion for precision and recall. Report only the held-out numbers.
Ownership answersThe case forbids silently assigning ownership, and the wireframe has a chip "Who should own Customer Profile schema?". The Ask agent answers with evidence-ranked candidates and the decision owner (RTE with Architect), never a single assignment.
DRI-X-006 data check"Identified after the event started" needs timestamps for when each dependency was first recorded relative to the event. If the data package lacks them, mark X-006 as illustrative or derive it from S8's recorded mid-PI blockers.
Mock labellingM2, M3 and M4 are generated, not provided. Label them as mocks in the demo so judges don't read X-007 or the Archer blocker as findings from real data.
  • Cheap additions that carry the production story: snapshot ID, prompt version and model version in every audit line; a visible degraded-mode banner; retrieved text delimited as data; rejected edges stored so they are not proposed again.

9. How to say it in the pitch

"What you are seeing runs on files because we don't have Haverstone's Jira. Underneath it is the same design Haverstone would deploy: a source adapter layer, a graph with evidence on every edge, deterministic risk rules, an LLM that only reads and explains, and a human gate before anything is committed. Moving to production means replacing the adapters on the bottom layer with read-only connectors. The agents, the rules, the screens and the audit trail do not change."
